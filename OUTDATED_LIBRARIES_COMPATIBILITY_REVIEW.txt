OUTDATED LIBRARIES COMPATIBILITY REVIEW
========================================

Review basis
------------
- OUTDATED_LIBRARIES_REPORT.txt is empty in the workspace; therefore this review was rebuilt from the direct PackageReference entries in swas.UI/swas.UI.csproj, swas.DAL/swas.DAL.csproj, and swas.BAL/swas.BAL.csproj.
- All three projects target net9.0.
- Latest-version values were checked against NuGet package metadata during this review. "Latest available" means latest stable version currently visible there, not a prerelease.
- "Latest compatible" means the latest package line that should be used while retaining net9.0. For Microsoft ASP.NET Core and EF Core packages, the 10.x line is treated as requiring net10.0 and is not reported as net9.0-compatible.
- Transitive packages are not listed as upgrade targets unless a corresponding direct reference is present. The resolved package graph is noted where it affects the recommendation.

Summary of important findings
-----------------------------
1. The report cannot be considered accurate because it contains no package records.
2. The Microsoft 9.x references are not automatically compatible with 10.x merely because both are NuGet packages. Keep the application on the 9.0.x servicing line unless the application is deliberately migrated to .NET 10.
3. Microsoft.AspNetCore.Antiforgery 2.3.11 is an especially concerning direct reference in a net9.0 ASP.NET Core application. Antiforgery is provided by the ASP.NET Core shared framework; the old 2.3.x package should not be used to pin an application component to an unrelated ASP.NET Core generation.
4. The UI project directly references both iText 8 package families: itext7/itext7.bouncy-castle-adapter and itext/itext.bouncy-castle-adapter. The BAL project also directly references itext7. This is a package-family duplication and should be resolved as a planned dependency change, not handled by blindly updating every iText package.
5. Grpc.Core is directly referenced by all three projects, but the resolved graph also contains Grpc.Core.Api. Grpc.Core is a legacy/deprecated gRPC implementation package; an upgrade is not available in the existing package line. Replacement with the supported Grpc.Net.Client stack is a code migration, not a simple version update.
6. Project-to-project references make some packages transitively available to the UI project. A package should remain a direct reference only where that project directly compiles against its API or needs its build/design-time behavior.

Direct/transitive observations
------------------------------
- swas.UI references swas.BAL and swas.DAL. Consequently, BAL and DAL package dependencies can appear in the UI resolved graph even when UI does not directly reference those packages.
- Dapper is direct in UI and BAL; Grpc.Core is direct in all three projects; iText is direct in UI and BAL; EF/Identity packages are duplicated between UI and DAL. These are direct-reference duplication candidates, not evidence that multiple runtime copies are required.
- Resolved transitive examples include BouncyCastle.Cryptography from the iText dependency graph, Grpc.Core.Api from Grpc.Core, and EF Core relational/abstractions/analyzer packages from the EF packages. Transitive entries should not be independently version-pinned unless the project has a demonstrated direct API dependency.
- The existing project files contain no central package-management file or lock file in the discovered project scope. Version alignment is therefore currently maintained manually.

Recommended order
-----------------
Immediate: update the Microsoft.AspNetCore/EF/Identity/NewtonsoftJson 9.0.x references as a coordinated set, using the latest 9.0.x-compatible versions and validating the application. Do not move those references to 10.x without first planning a net10.0 migration.

Planned: resolve iText package-family duplication; review Grpc.Core replacement; remove redundant direct references after checking API usage; update Bootstrap, Dapper, Newtonsoft.Json, BouncyCastle, and code-generation packages where they are actually needed.

Do Not Upgrade Now: Microsoft.AspNetCore.Antiforgery as a standalone 2.x package. Treat it as a framework-provided component and separately verify whether the direct reference can be removed in a future controlled change.
